# Write PRD

Use this skill when the user wants to draft or improve a product requirements document (PRD).

Write a concise PRD in this order:

## Context

- State the proposal in direct, plain language for the widest audience first.
- Explain why it matters now and why this approach makes sense.
- Prefer durable reasoning that is unlikely to change during execution.
- Include concise details such as the problem, solution, alternatives considered, prior art, or customer-facing framing when they help clarify the decision.

## Usage scenarios

- Describe concrete situations involving real users.
- Show who the feature is for, what they are trying to do, and how the change helps.
- Keep each scenario specific and easy to picture.

## Issues

- Outline the execution path as staged deliverables that reflect sequencing, dependencies, and risk reduction.
- Write every work item as a literal bullet that can be converted into an issue.
- Start each bullet with an action-oriented issue title, followed by a short description.
- Keep issue phrasing concise and close to real implementation work, not broad roadmap milestones.
- Put this section last because issue details are most likely to change during implementation.

## Writing rules

- Use direct, plain language, short sentences, and simple wording.
- Avoid jargon unless it is needed for accuracy.
- Move from broad audience and high-level context to specific scenarios and implementation details.
- Keep the PRD concise, decision-oriented, and easy to scan.
- Do not invent user needs, decisions, or constraints. Mark assumptions clearly or ask a focused question when a missing fact would change the proposal.

End with a PRD that is ready to turn into implementation issues.
